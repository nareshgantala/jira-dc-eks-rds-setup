Card 1 What is the fundamental difference between EKS Cluster Role and Node Group Role?
  • EKS Cluster Role (Control Plane):
    • Assumed by: AWS EKS managed service (eks.amazonaws.com).
    • Purpose: Grants Kubernetes control plane components (API server, controller manager) permissions to manage AWS resources (e.g. cross-account ENIs, load balancers, security groups).
  • EKS Node Group Role (Worker Nodes):
    • Assumed by: EC2 Worker instances (ec2.amazonaws.com).
    • Purpose: Allows the node kubelet to join the cluster, enables VPC CNI to manage secondary pod IPs, and allows pulling images from Amazon ECR.
Card 2 Which AWS managed policy is strictly required for the EKS Cluster Role?

AmazonEKSClusterPolicy

Provides Kubernetes with permissions to manage networking components required for cluster operation, such as ENIs attached to your subnets for control plane-to-worker communication and security group interactions.

Card 3 What are the 3 mandatory AWS managed policies for EKS Worker Nodes?
  1. AmazonEKSWorkerNodePolicy: Allows worker node kubelet to communicate with the EKS control plane API server.
  2. AmazonEKS_CNI_Policy: Grants the AWS VPC CNI plugin (aws-node) permissions to allocate and attach secondary ENIs/IPs on the node for Pods.
  3. AmazonEC2ContainerRegistryReadOnly: Allows worker nodes to pull container images from Amazon ECR.

(Optional Bonus: AmazonSSMManagedInstanceCore allows accessing nodes via AWS Systems Manager Session Manager without needing SSH keys).

Card 4 Why must aws_eks_cluster and aws_eks_node_group declare depends_on for IAM policy attachments?
  • The Problem: IAM role creation and policy attachments are separate asynchronous AWS API operations. IAM changes take seconds to propagate globally.
  • The Failure: Without explicit depends_on, Terraform begins provisioning the EKS cluster or node group before AWS IAM policies are active, triggering ResourceInitializationError or authorization failures.
  • Fix: 
    resource "aws_eks_cluster" "main" {
  ...
  depends_on = [
    aws_iam_role_policy_attachment.cluster_AmazonEKSClusterPolicy
  ]
}
Card 5 What are the subnet and AZ requirements for Amazon EKS?
  • Multi-AZ: EKS requires subnets in at least two different Availability Zones (3 AZs recommended for production high availability).
  • Subnet Sizing: Minimum /28 (16 IPs), but /24 (256 IPs) is strongly recommended because AWS VPC CNI allocates a real VPC IP address to every individual Pod.
  • Control Plane ENIs: EKS automatically places redundant cross-account ENIs across the specified subnets in your VPC.
Card 6 Why is attaching application policies to the Node Group IAM Role an anti-pattern? What is the alternative?
  • Anti-pattern Risk: Any policy attached to the Node Group IAM role is shared across all Pods running on that node, violating least privilege.
  • The Modern Solution: Use IRSA (IAM Roles for Service Accounts) or EKS Pod Identity:
    • Enables an OpenID Connect (OIDC) provider on EKS.
    • Maps an IAM role directly to a specific Kubernetes ServiceAccount.
    • Only authorized Pods (e.g. Jira Pods needing EFS/S3) receive credentials.
Card 7 What storage architecture is required for Jira Data Center on EKS?
  • jira-local-home (Per Pod):
    • Storage: Fast block storage via Amazon EBS (gp3) with ReadWriteOnce (RWO).
    • Content: Search indexes (Lucene), caches, and local runtime logs.
  • jira-shared-home (Shared Across Cluster):
    • Storage: Shared network filesystem via Amazon EFS with ReadWriteMany (RWX) using the AWS EFS CSI Driver.
    • Content: Attachments, avatars, plugins, and cluster locks accessible concurrently by all Jira nodes.
Card 8 How does EKS Access Entries replace the legacy aws-auth ConfigMap?
  • Legacy (aws-auth ConfigMap): Required modifying a ConfigMap in Kubernetes kube-system to map IAM ARNs to RBAC. It was difficult to manage with Terraform and prone to syntax lockouts.
  • Modern (EKS Access Entries): Standardized AWS API resources (aws_eks_access_entry and aws_eks_access_policy_association) that allow managing cluster access directly in Terraform without interacting with Kubernetes internal ConfigMaps.
Card 9 If we already have Cluster & Node IAM roles, why do we still need an OIDC Provider?

EKS security operates across 3 distinct layers:

  1. EKS Cluster Role: Used exclusively by the AWS-managed Control Plane (eks.amazonaws.com) to manage cross-account ENIs and ELBs. Pods cannot use it.
  2. Node Group Role (EC2 Instance Profile): Used by the EC2 host OS and kubelet to join the cluster, assign VPC IPs via CNI, and pull images from ECR.
  3. Pod-Level IAM (IRSA via OIDC): If you attach application policies (e.g. EBS/EFS/S3) to the Node Group role, every pod on that EC2 instance inherits those permissions, creating a critical security vulnerability.

Why OIDC is mandatory: The OIDC Provider establishes cryptographic federated trust between EKS and AWS IAM, enabling IRSA (IAM Roles for Service Accounts) so that only specific, designated pods get granular AWS IAM permissions.

Card 10 What is the step-by-step authentication flow of IRSA via OIDC under the hood?
  1. Projected Token Injection: Kubernetes automatically projects an OIDC JSON Web Token (JWT) into the pod at /var/run/secrets/eks.amazonaws.com/serviceaccount/token.
  2. SDK Call: The AWS SDK inside the pod calls AWS STS via sts:AssumeRoleWithWebIdentity, sending the JWT and the target IAM Role ARN.
  3. Cryptographic Verification: AWS STS contacts the cluster's OIDC Provider endpoint to verify the JWT signature against the cluster's public keys.
  4. Trust Policy Evaluation: STS validates the IAM Role trust condition matching the token subject: system:serviceaccount:<namespace>:<name>.
  5. Temporary Scoped Credentials: STS issues short-lived, auto-rotating AWS credentials (AccessKey, SecretKey, SessionToken) strictly to that specific pod.

Key Advantage: Zero long-term AWS access keys stored in code, configmaps, or container images.

Card 11 What is the IMDS security vulnerability, and how do IMDSv2 and OIDC protect against it?
  • The Vulnerability: Any container on an EC2 instance can query the EC2 Instance Metadata Service (http://169.254.169.254/latest/meta-data/iam/security-credentials/) and steal the node's IAM credentials. If the node role has EBS, EFS, or S3 write access, any compromised pod inherits full AWS access.
  • Defense 1 (IMDSv2 Hop Limit): Configure http_put_response_hop_limit = 1. Network packets crossing the container bridge network decrement IP TTL by 1, blocking pods from reaching the metadata IP while allowing the host EC2 OS to access it.
  • Defense 2 (IRSA via OIDC): Keeps the Node Group IAM Role strictly scoped to base infrastructure (EKSWorkerNodePolicy, CNI_Policy, ECRReadOnly) and delegates application permissions strictly to individual ServiceAccounts.
Card 12 How do you configure the EKS OIDC Provider and an IRSA IAM Trust Policy in Terraform?

1. Create the OIDC Provider:

data "tls_certificate" "eks" {
  url = aws_eks_cluster.main.identity[0].oidc[0].issuer
}

resource "aws_iam_openid_connect_provider" "eks" {
  client_id_list  = ["sts.amazonaws.com"]
  thumbprint_list = [data.tls_certificate.eks.certificates[0].sha1_fingerprint]
  url             = aws_eks_cluster.main.identity[0].oidc[0].issuer
}

2. Pod IAM Role Trust Policy:

assume_role_policy = jsonencode({
  Version = "2012-10-17"
  Statement = [{
    Action    = "sts:AssumeRoleWithWebIdentity"
    Effect    = "Allow"
    Principal = { Federated = aws_iam_openid_connect_provider.eks.arn }
    Condition = {
      StringEquals = {
        "${replace(aws_iam_openid_connect_provider.eks.url, "https://", "")}:sub" = "system:serviceaccount:kube-system:ebs-csi-controller-sa"
        "${replace(aws_iam_openid_connect_provider.eks.url, "https://", "")}:aud" = "sts.amazonaws.com"
      }
    }
  }]
})
Card 13 Which components in Jira Data Center on EKS require IRSA via OIDC?
  • AWS EBS CSI Driver (ebs-csi-controller-sa): Policy AmazonEBSCSIDriverPolicy to dynamically provision and attach EBS gp3 volumes for jira-local-home (RWO).
  • AWS EFS CSI Driver (efs-csi-controller-sa): Policy AmazonEFSCSIDriverPolicy to automatically mount the shared EFS filesystem for jira-shared-home (RWX).
  • AWS Load Balancer Controller: Custom ALB IAM Policy to discover Ingress resources and automatically provision the Application Load Balancer with cookie-based sticky sessions.
  • Jira Core Application Pods: Zero direct AWS IAM permissions needed. They only communicate with RDS (PostgreSQL) and mounted filesystem paths, following strict Principle of Least Privilege.
