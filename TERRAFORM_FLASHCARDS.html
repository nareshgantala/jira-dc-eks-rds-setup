📚 Terraform Flashcards: Providers & Backend

Card 1 What is the difference between the required_providers block and the provider "aws" block?
  • required_providers (Declaration): Specifies which plugin binary to download from the registry, its source (hashicorp/aws), and version constraints (~> 6.0).
  • provider "aws" (Runtime Configuration): Configures how the downloaded plugin interacts with the AWS API (e.g. target region = "us-east-1", credentials, assume roles, default tags).
Card 2 What does source = "hashicorp/aws" mean and what is its standard address format?

It tells Terraform where to download the provider plugin from in the registry.

  • Format: [<HOSTNAME>/]<NAMESPACE>/<TYPE>
  • Hostname: Defaults to registry.terraform.io if omitted.
  • Namespace: hashicorp (the organization).
  • Type: aws (the provider name).
  • Full Address: registry.terraform.io/hashicorp/aws
Card 3 What does the pessimistic version constraint ~> 6.0 mean vs ~> 6.0.0?
  • ~> 6.0 allows minor & patch updates: >= 6.0.0, < 7.0.0 (allows 6.1.0, blocks breaking major changes in 7.0.0).
  • ~> 6.0.0 allows patch updates only: >= 6.0.0, < 6.1.0 (allows 6.0.1, blocks 6.1.0).
Card 4 Can backend "s3" be nested inside required_providers? Where should it live?

No. Nesting backend inside required_providers causes a syntax error.

  • required_providers and backend must be sibling blocks inside the root terraform { ... } block.
  • Only one backend block is permitted per root module configuration.
Card 5 How does state locking work for S3 backend? Is enable_locking = true valid?
  • enable_locking is invalid syntax and not supported by the S3 backend.
  • Terraform 1.10+: Supports native S3 state locking via use_lockfile = true (no DynamoDB table required).
  • Terraform < 1.10 / Classic: Requires an Amazon DynamoDB table configured with dynamodb_table = "<table-name>".
Card 6 Why can't you use variables (e.g. var.environment) inside a backend "s3" block?

Terraform initializes the backend during the very first phase of execution, before variables, locals, or resource configs are parsed and loaded.

Because variables do not exist yet when the backend initializes, values must be passed statically or via Partial Backend Configuration.

Card 7 What is "Partial Backend Configuration" and why is it used?
  • Definition: Defining an empty backend block in code (backend "s3" {}) and supplying environment-specific values (bucket, key, region) at runtime via an external .tfvars file.
  • Benefit: Keeps the codebase DRY and environment-agnostic, allowing one set of Terraform files to deploy across dev, qa, and prod without duplicate code.
Card 8 What CLI commands are used to initialize and switch environments with partial backend config?

1. Initialize Dev:

terraform init -backend-config="env/dev/backend.tfvars"

2. Switch to Prod:

terraform init -backend-config="env/prod/backend.tfvars" -reconfigure

(The -reconfigure flag tells Terraform to discard the cached backend connection and point cleanly to the new state file).
